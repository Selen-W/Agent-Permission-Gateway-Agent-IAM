## 1. 安装与挂载

插件是标准 Cordis 插件（导出 `name` / `inject` / `apply`），**零运行时依赖**，通过
结构类型契约对接宿主，不 import 任何 harness 包。

### 方式一：作为 out-of-tree 插件挂载（推荐）

把整个项目（或仅 `src/`）放到你的部署里，在 dsh 的 `cordis.patch.yml` 中挂载：

```yaml
# cordis.patch.yml（dsh profile 的补丁层）
plugins:
  permission-gateway:
    $apply: ./agent_job_permission_dev/src/index.ts   # 或打包后的入口
    policy: |
      agent: coding-agent
      default_decision: ask
      permissions:
        shell:
          allow: ["git status", "git diff", "npm test"]
```

插件声明 `inject: ['tools']`，宿主启动时会在工具注册表就绪后调用 `apply(ctx)`。

### 方式二：并入 harness 源码包

`src/` 的类型与 `@deepseek-ai/dsh-permission-gateway/types` 完全兼容，可以直接把
`src/` 内容放入 harness 的 `packages/permission-gateway/src/`（该包当前只有
`types.ts`），按 harness 的 workspace 规范构建。

### 配置来源与生效顺序

| 层 | 来源 | 说明 |
|---|---|---|
| 组合层（base） | `ctx.config`（`cordis.patch.yml` 的插件配置） | `policy` 可以是 **YAML 字符串**或**对象** |
| 用户层（overlay） | settings 命名空间 `permission-gateway` | 注册成功时，用户文档覆写 base；`applies: live` 即时生效 |

> settings 集成是 best-effort：宿主没有 `ctx.settings` 时自动跳过，不影响功能。

### 最小可用配置

```ts
// ctx.config
{
  policy: {
    agent: 'coding-agent',
    operator: 'alice',
    default_decision: 'ask',
    permissions: {
      filesystem: { read: ['./workspace/**'], write: ['./workspace/**'] },
      shell: { allow: ['git status', 'git diff', 'npm test'], deny: ['sudo', 'rm -rf /'] },
    },
  },
}
```

不配置任何策略也能用：所有调用按 `defaultDecision: 'ask'` 走批准，风险 ≥ 80 直接拒绝——
默认就是 fail-closed 的。

## 2. 配置参考

插件配置即 `GatewayConfig`（`src/types.ts`）：

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `rules` | `GatewayRule[]` | `[]` | 直接提供编译好的规则（跳过 policy 文档）；与 `policy` 同时存在时，规则列表就是 `settings.rules` |
| `policy` | `PolicyDocument` \| string | 无 | 声明式策略文档（YAML 字符串或对象），编译为 `rules` |
| `defaultDecision` | `'allow' \| 'ask' \| 'deny'` | `'ask'` | 无规则命中时的姿态；`'deny'` 即白名单模式 |
| `denyRiskAbove` | number | `80` | 风险熔断上限（0-100）；无显式规则命中且分数 ≥ 该值时 DENY |
| `operatorName` | string | 无 | 受信任操作者；风险模型给其 −5 信用分 |
| `risk` | `RiskModelConfig` | 见下文 | 风险模型旋钮 |
| `ringSize` | number | `500` | 进程级审计环容量 |
| `grantShortCircuit` | boolean | `true` | 是否注册 `approval/request` 授权短路监听器 |

### `RiskModelConfig` 字段

| 字段 | 类型 | 默认 | 说明 |
|---|---|---|---|
| `productionWindow` | `string[]` | 无 | 生产窗口，如 `["09:00-18:00 Mon-Fri"]`；窗口外触及生产 +20 |
| `taskRelevance` | boolean | `true` | 是否启用 WHY 维度（任务相关性） |
| `identity` | boolean | `true` | 是否启用 WHO 维度（身份） |
| `operationBase` | `Partial<Record<OperationKind, number>>` | 内置表 | 覆盖各操作基础分 |
| `resourceSensitivity` | `Partial<Record<ResourceKind, number>>` | 内置表 | 覆盖各资源敏感度 |

## 3. 策略文件完整参考

### 顶层字段

```yaml
agent: coding-agent          # 受管辖的 Agent 名（可数组）；用于 WHO 识别
default_decision: ask        # allow | ask | deny
deny_risk_above: 80          # 风险熔断
operator: alice              # 受信任操作者
production: {...}            # 生产策略（见下）
permissions: {...}           # 各能力分区
```

### `production` 生产策略

| 字段 | 类型 | 说明 |
|---|---|---|
| `require_approval` | boolean | 所有触及生产的调用 → ASK |
| `protected_branches` | string[] | 受保护分支 glob（`main`、`prod/*`）；写这些分支 → ASK |
| `window` | string[] | 生产窗口 `"HH:MM-HH:MM DDD[,DDD]"`；窗口外触及生产风险 +20 |

### `permissions` 能力分区

| 分区 | 匹配对象 | 列表字段 | 说明 |
|---|---|---|---|
| `filesystem` | 路径 glob | `read` / `write` / `delete` / `approval` / `deny` | **按操作分类**：`read` 只匹配读调用，`write` 只匹配写调用，`delete` 只匹配删调用 |
| `shell` | 命令 token | `allow` / `approval` / `deny` | 任意携带 shell 命令的调用（`bash`、`terminal`、`run_*`…） |
| `network` | 主机 glob | `allow` / `approval` / `deny` | 网络调用（`http.*` 工具或 `curl` 等命令） |
| `repository` | 命令 token | `allow` / `approval` / `deny` / `protected_branches` | git 命令；比通用 `shell` 更特异 |
| `database` | 命令 token | `allow` / `approval` / `deny` | `psql` / `mysql` / `sqlite3` / `mongosh` 等 |
| `deploy` | 命令 token | `allow` / `approval` / `deny` | `kubectl` / `terraform` / `aws` / `heroku` 等 |
| `production` | — | `require_approval` 等 | 见上；也可写在 `permissions.production` |

### 匹配语义

**命令（token 前缀匹配）**

- `git push` 匹配 `git push origin main`，**不**匹配 `git pushy branch`
- token 内支持 glob：`rm -rf *`、`git checkout feature/*`
- 引号内是一个整体 token：`echo "hello world"` 只匹配 `echo "hello world"`；
  SQL 里写 `psql -c SELECT*` 以匹配 `psql -c "SELECT * FROM users"`

**路径 / 主机 / 分支（glob）**

- 路径：`./workspace/**`、`/etc/**`（`*` 不跨 `/`，`**` 跨 `/`，支持 `?` 与 `{a,b}`）
- 主机：`github.com` 自动匹配子域 `api.github.com`；`*.npmjs.org` 精确匹配该层级
- 分支：`main`、`feature/*`、`prod/*`

### 优先级与求值顺序（重要）

1. **带内优先级（默认）**：`deny > approval > allow` —— 最严格者胜出。
2. **`deny: ["*"]` 是"默认拒绝"**：检测到 deny 列表含 `*`/`**` 时改为
   `allow > approval > deny`，显式 allow 列表优先，未列出的才落入拒绝（网络白名单写法）。
3. **能力特异性**：求值顺序为
   `filesystem → repository → database → deploy → network → shell → protected_branches → production`。
   所以 `repository.deny: ["git push --force"]` 能盖过 `shell.approval: ["git push"]`。
4. **风险熔断**：没有任何规则命中且 `score ≥ deny_risk_above` → DENY；**显式规则命中可覆盖熔断**
   （规则是人的审慎决定，比如 production `require_approval` 规则命中时即使分数 100 也只 ASK 不 DENY）。
5. **授权短路**：ASK 判定后先查有界授权，命中即 ALLOW。

见 [`examples/policy.example.yaml`](../examples/policy.example.yaml)。用
`pnpm exec tsx examples/demo.ts` 可以直接看到每条规则的判决与风险分解。

## 4. 风险引擎详解

风险引擎只产生**证据**（分数、档位、flags、逐项原因），**不裁决**；裁定始终由策略与操作者作出。

### 评分模型

```
score = clamp(0..100,
    WHAT 基础分        // read 0 / write 10 / execute 15 / network 20 / delete 25 / deploy 30
  + WHERE 敏感度       // workspace 0 / repository 10 / network 15 / system 25 / database 30 / production 45
  + WHEN 窗口惩罚      // 生产调用落在窗口外 +20
  + WHY 任务不匹配     // 动作与当前任务关键词重合度 < 0.25 → +15
  + WHO 身份           // 未识别主体 +5；操作者本人 −5
  + flags×5            // 每个风险旗标 +5
)
```

| 分数 | 档位 |
|---|---|
| < 25 | `low` |
| < 50 | `medium` |
| < 75 | `high` |
| ≥ 75 | `critical` |

### 风险旗标（flags）

`destructive-remove`（`rm -r*`）、`privilege-escalation`（`sudo`/`chmod 777`/`docker exec`）、
`network-egress`（`curl`/`wget`/`nc`/`ssh`）、`credential-access`（`AKIA…`/`password=`/`.env`）、
`database-write`（`DELETE FROM`/`DROP TABLE`/`UPDATE…SET` 无 WHERE）、`broad-wildcard`
（`rm -rf /`）、`production-access`、`protected-branch`、`outside-production-window`、
`action-not-in-task-scope`、`unrecognized-principal`。

> 每条 flag 都会出现在审计记录里，UI 可以直接渲染成"风险理由"。

### WHY：任务相关性

- 任务文本来自会话日志中最近一条 `user/message`（可被 `judgeCall(..., { task })` 显式覆盖）。
- `taskRelevance(task, action)` 计算任务关键词（去停用词）在动作文本中的命中比例。
- 重合度 < 0.25 判定为"任务不匹配"，风险 +15 —— 这正是
  "任务写着修测试，Agent 却 `aws s3 rm production-bucket`" 这类越界行为的探测器。

### 生产窗口

格式 `"HH:MM-HH:MM DDD[,DDD]"`，`DDD` 为 `Mon`..`Sun` 或区间 `Mon-Fri`，缺省为周一至周五。
只有 `WHERE = production` 且配置了窗口时才参与评分。

## 5. 批准与作用域授权

### 批准流程

当判决为 ASK 时，插件返回 `{ kind: 'ask', reason }`，由宿主工具注册表的既有批准通道接管：

```text
tools/pre-execute ── ASK ──► approval/request 瀑布
                                │
                    ┌───────────┼──────────────┐
                    ▼           ▼              ▼
              allowed-once   rejected      cancelled/unavailable
                （执行一次）  （拒绝执行）    （无通道 → fail-closed 拒绝）
```

批准问题与结果会以 `approval/asked` + `approval/decided` 事件写入会话日志（审计）。

### 一次性批准 ≠ 有界授权

- **Approve once**：只放行当前这一次调用，不留任何状态。
- **Always allow（有界授权）**：`mintGrant()` 铸造一个授权，后续调用在
  **Action + Resource + Scope + Time** 全部命中的情况下自动 ALLOW，不打扰用户。

```ts
const grant = service.mintGrant({
  action: 'git push*',                             // Action：命令前缀（token 语义）
  scope: {                                         // Scope：
    resource: 'github.com/company/project-a',      //   Resource 边界
    branch: 'feature/*',                           //   分支边界
    agent: 'coding-agent',                         //   Agent 边界
  },
  durationMs: 3_600_000,                           // Time：1 小时后过期
  grantedBy: 'alice',                              // 谁铸造的
  reason: 'feature 分支推送获批',
})
```

匹配规则：授权必须**同时**满足 action / tool / resource / branch / agent / 未过期 才生效；
任何一个维度不符（比如推 `main` 而授权只覆盖 `feature/*`）都不命中。过期授权在每次访问时
惰性清理。

### 授权短路（grantShortCircuit）

`approval/request` 监听器在宿主批准 UI 之前检查授权：

- 命中有界授权 → 直接返回 `'allowed-once'`（不弹窗）
- 未命中 → `next()` 交给宿主批准通道（弹窗 / fail-closed）

"Always allow" 的 UI 按钮（你的 mockup 里的第二个按钮）只需调用 `service.mintGrant(...)`
即可落库，之后所有匹配调用静默放行。

## 6. 审计与可观测性

每一次到达网关的调用都会产生一条审计记录，写入两个地方：

### 1. 会话日志（持久、可重放）

```
permission/gateway-decision   ← log-only，永不出现在模型上下文
```

```ts
{
  callId: 'c42', tool: 'bash',
  risk: { score: 80, level: 'critical', flags: ['production-access'], reasons: [...] },
  decision: 'ask', ruleId: 'rule-31', grantId: undefined,
  granted: false, reason: 'production-touching calls require approval',
}
```

### 2. 进程级审计环（浏览器/面板用）

| API | 说明 |
|---|---|
| `service.recentAudit(limit = 50)` | 最近的审计记录，新→旧 |
| `service.summary()` | `{ ruleCount, defaultDecision, denyRiskAbove, operatorName?, activeGrantCount, ringSize }` |
| `ctx.permissionGateway` | 注册在宿主上下文上的服务引用 |

### 3. 会话投影

插件注册 `permissionGateway` 投影（key），按会话折叠最近 50 条决策（新→旧），
浏览器端审计面板与重放共用同一份数据。

## 7. 编程接口参考

`PermissionGatewayService`（`src/service.ts`）暴露在 `ctx.permissionGateway`：

| 方法 | 签名 | 说明 |
|---|---|---|
| `judgeCall` | `(call: {name, arguments}, extra?: ExtractOptions) => GatewayJudgement` | 判案但不落审计（预览/测试） |
| `judgeExecution` | `(exec: ToolExecutionLike) => {decision, judgement, request}` | 判案 + 落审计（插件内部使用） |
| `previewRisk` | `(call, extra?) => RiskAssessment` | 只看风险，不看判决 |
| `summary` | `() => GatewaySummary` | 姿态摘要 |
| `recentAudit` | `(limit?) => PermissionAuditEntry[]` | 审计环 |
| `mintGrant` / `revokeGrant` / `listGrants` | — | 有界授权管理 |
| `setPolicyDocument` | `(document) => void` | 运行时热更新策略 |
| `setOverlay` | `(settings?) => void` | 运行时覆写设置（settings 命名空间回调用） |
| `knownAgents` | `() => readonly string[]` | 策略管辖的 Agent 名（WHO 识别用） |
| `settings` | getter | 当前生效的 `GatewaySettings` |

`ExtractOptions`（`src/context.ts`）可覆盖：`now`、`task`、`agentId`、`agentName`、
`operatorName`、`sessionId`、`productionWindow`、`knownAgents`。

`GatewayJudgement`：`{ decision: 'allow'|'deny'|'ask', reason?, ruleId?, grantId?, risk }`。

## 8. 常见场景

### 场景一：只读编码助手（白名单模式）

```yaml
agent: coding-agent
default_decision: deny          # 白名单：没写进 allow 的一律拒绝
permissions:
  filesystem:
    read: ["./workspace/**"]
  shell:
    allow: ["git status", "git diff", "git log", "npm test"]
```

效果：Agent 只能读 workspace 与跑测试；任何写操作、网络、sudo 直接 DENY。

### 场景二：CI / 无人值守

- 宿主侧把会话批准策略设为 `never`（`approval/policy` 事件），ASK 一律确定性拒绝；
- 网关侧 `default_decision: deny` + 严格 allow 列表；
- 需要放行的操作显式写进 allow（如 `npm publish` 走审批人预置的 grant）。

### 场景三：生产环境保护

```yaml
default_decision: ask
production:
  require_approval: true
  protected_branches: ["main", "master", "prod/*"]
  window: ["09:00-18:00 Mon-Fri"]
permissions:
  deploy:
    allow: ["kubectl get", "kubectl describe", "terraform plan"]
    approval: ["kubectl apply", "terraform apply"]
    deny: ["kubectl delete namespace", "terraform destroy"]
```

效果：生产操作必须人工批准；非工作时段的生产操作风险 +20；受保护分支写操作必须批准。

### 场景四：网络出口白名单

```yaml
permissions:
  network:
    allow: ["github.com", "registry.npmjs.org", "pypi.org"]
    deny: ["*"]        # 默认拒绝一切未列出的主机
```

### 场景五：数据库只读代理

```yaml
permissions:
  database:
    allow: ["psql -c SELECT*", "mysql -e SHOW*"]
    approval: ["psql -c INSERT*", "psql -c UPDATE*"]
    deny: ["psql -c DROP*", "psql -c TRUNCATE*", "mysql -e DROP*"]
```

## 9. 常见问题 FAQ

**Q：为什么不能简单地把 `git` 全放行、`rm` 全拒绝？**
因为 `git push` 到 `feature/*` 与 `git push` 到生产分支风险完全不同。网关把 WHO/WHAT/WHERE/
WHEN/WHY 五个维度都纳入评分与规则匹配，同一个命令在不同上下文得到不同判决。

**Q：`deny: ["*"]` 和 `deny: ["sudo"]` 有什么区别？**
`deny: ["*"]` 是"默认拒绝"标记：它让 allow 列表优先，未列出的才拒绝（白名单模式）。
`deny: ["sudo"]` 是特定禁止：它盖过 allow 列表（最严格者胜出）。

**Q：ASK 会不会卡住不返回？**
不会。宿主批准通道 fail-closed：没有 ApprovalService → 直接 DENY；没有可用的 answerer →
`unavailable` → DENY。网关自身不持有批准会话。

**Q：风险引擎会直接拒绝调用吗？**
不会。风险只是证据。只有（a）显式 deny 规则命中，或（b）无规则命中且分数 ≥ `deny_risk_above`，
才会 DENY。显式 allow/ask 规则可以覆盖熔断。

**Q：如何让"Always allow"落地？**
批准 UI 的"Always allow"按钮调用 `service.mintGrant({ action, scope, durationMs, grantedBy })`。
之后匹配的调用在授权有效期内自动 ALLOW。

**Q：授权会不会永久有效？**
不会。每个授权都有 `expiresAt`（`createdAt + durationMs`），过期自动失效并被惰性清理。
授权还受 resource/branch/agent 边界约束，不是全局放行。

**Q：策略改了需要重启吗？**
不用。`service.setPolicyDocument(document)` 可热更新；settings 命名空间注册后用户改文档
即时生效（`applies: live`）。

**Q：为什么 YAML 解析器不支持锚点/多行字符串？**
策略文件极小且是安全边界：解析错一个 `*` 就可能开错一扇门。解析器宁可抛错（带行号）也不
静默误解析。需要复杂结构时用 flow 语法 `[a, b]` / `{k: v}` 或直接传 JS 对象。
